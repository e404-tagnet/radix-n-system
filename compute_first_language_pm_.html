AXON — Compute-First Programming Language
A language whose semantics derive from machine architecture, not human metaphor.
StatusPre-Discovery
Phase0 — Framing
OwnerTBD
Last revised2026-03-16
Horizon18–36 months (research-grade)
Problem statement
›All mainstream languages encode human cognitive habits: named variables, linear text, sequential metaphor, base-10 assumptions, natural-language syntax.
›The result: compilers spend enormous effort translating human-legible abstractions back into what the machine actually wants — registers, pipelines, memory hierarchies, instruction parallelism.
›Hypothesis: a language whose primary abstraction layer mirrors the machine's actual execution model could eliminate whole classes of translation overhead and expose optimisation space that no human would naturally write toward.
›Secondary hypothesis: a sufficiently disciplined human-interface layer can be generated on top, making the language practically usable without corrupting its foundations.
Phases & scope
PHASE 0 Needs + constraint analysis Blocker
Must complete before any design decisions. Defines what "compute-first" actually means in practice and surfaces inherited constraints that cannot be designed away.
–Survey existing compute-native work: LLVM IR, SPIR-V, WebAssembly, Forth, APL, J, Futhark, Halide, MLIR. What did they get right? Where did human-bias creep back in?
–Hardware landscape mapping: x86-64, ARM, RISC-V, GPU (CUDA/ROCm), neuromorphic (Intel Loihi, IBM TrueNorth), ternary (Setun lineage, experimental). Language must have a clear target or it designs for nothing.
–Define "maximising compute potential" with measurable criteria — throughput? latency? energy per operation? instruction-level parallelism exposure? Without this, the goal is unfalsifiable.
PHASE 1 Core compute model Design
Define the language's fundamental unit of computation, not its syntax. Answer: what is a "thing" in this language — a signal, a tensor, a stream, a state transition?
–Execution model: dataflow graph vs. continuation-passing vs. SSA-native vs. actor model vs. hardware description logic
–Type system: should types encode physical constraints (bit width, memory location, cache tier, alignment) rather than semantic categories?
–Memory model: flat, hierarchical, ownership, capability-based — or let the machine dictate and surface that explicitly?
–Concurrency primitive: is parallelism a first-class citizen at the syntax level, not an afterthought library?
PHASE 2 Semantics + syntax Design
Only once Phase 1 is stable. Syntax is the least important layer — it will change. Semantics are load-bearing and expensive to revise.
–Formal semantics first (operational or denotational). No ambiguity in what a program means.
–Surface syntax designed as a view over the semantic graph — not as the ground truth. Multiple syntaxes over the same IR are a feature, not a bug.
–Decide: is the canonical representation textual, binary, or graph-structured? Text is human bias — acknowledge that choice explicitly.
PHASE 3 Human interface layer Integration
Built last, kept separate. The interface should be generatable — ideally by a tool or AI layer — without contaminating the core model.
–Readable notation: compact, dictionary-style, no prose keywords. Terse is correct here — APL/J aesthetics are closer to truth than Python's.
–Tooling: visualiser that shows the execution graph, not the text. Humans navigate graphs poorly via text.
–AI-assisted compilation: if the target is AI-generated code, the "human interface" may be natural language to IR — skip readable syntax entirely as a strategic option.
PHASE 4 Prototype runtime Build
Interpreter or JIT on a single target first. Not production-ready — proof of semantic coherence and measurable performance delta vs. a compiled C baseline.
Deliverables — prioritised
D1
Needs analysis doc
What problems is this solving. Measurable success criteria. Target hardware. Comparison against LLVM IR / MLIR / Wasm as the honest baseline.
D2
Constraint register
Physical constraints (clock, memory bandwidth, instruction set), human constraints (who will ever use this and why), toolchain constraints (bootstrapping problem).
D3
Execution model specification
Formal description of what a program is in this language — independent of any syntax. This is the intellectual core of the project.
D4
Type system + memory model spec
Physical-property type system. Ownership or capability model. Cache-tier annotations.
D5
Reference syntax (v0.1)
Minimal, terse, reversible — a notation for the IR. Not "the language". Subject to wholesale replacement.
D6
Proof-of-concept interpreter
Single target (x86-64 or RISC-V). Benchmarked against equivalent C. The benchmark is the only thing that matters at this stage.
Constraint analysis
HardYou still need a bootstrapping compiler — written in something. First implementation will be human-biased by necessity. This is the serpent eating its own tail and you cannot design your way out of it.
HardBinary hardware is a constraint, not a choice. The machine is human-designed. "Computer-first" means optimising within those constraints, not transcending them.
HardWithout an ecosystem (libraries, tooling, community) adoption is zero. A perfect language no one uses is an academic paper. Decide upfront: research artefact or practical tool. Different designs.
StructuralMLIR and LLVM IR already exist and are already closer to machine representation than any high-level language. The honest question is: what would this language do that they don't?
StructuralTernary is currently theoretical at scale. Designing for it now is speculative. Either commit to binary with a clean ternary migration path, or treat ternary as a separate research thread.
BiasThe very act of designing a language is a human act. "Computer-first" is a design philosophy, not an escape from human authorship. Name this honestly — the goal is minimising anthropocentric bias, not eliminating the designer.
Key risks
Scope drift High
Without a fixed target architecture the design space is infinite. Lock hardware target in Phase 0 or the project never converges.
Reinventing MLIR Medium
MLIR is a multi-level IR with a pluggable dialect system. Due diligence required to show differentiation before building from scratch.
No adoption path High
If the human interface is left too late, the language will never be validated against real workloads. Phase 3 needs a usability MVP, not a perfect interface.
Unfalsifiable goal Medium
"Maximise computer potential" is not measurable. D1 must define specific, quantitative success criteria or every design decision becomes an argument.
Open questions — need answers before Phase 1
① What is the primary target architecture? The answer shapes every design decision downstream.
② What does "maximising compute" mean in numbers? Throughput? Energy per FLOP? Instruction-level parallelism score?
③ How does this differentiate from MLIR / LLVM IR? This is the hardest question and must be answered honestly.
④ Research artefact or practical tool? The answer determines whether Phase 3 matters or is optional.
⑤ Is AI the intended "human" interface? If code is generated by an LLM anyway, readable syntax becomes optional infrastructure.
Working title AXON — subject to change. All phase estimates assume a single experienced language designer; team size scales timelines.
